# Evaluating the `crm` skill: paired-condition behavioral eval on the live-e2e infra, plus a static best-practices lint

> **Supersedes the behavioral half of [ADR 0015](0015-skill-evaluation-static-gate-plus-behavioral-eval.md) and all of [ADR 0016](0016-skill-efficacy-review-persist-then-analyze.md).**
> ADR 0015's **Machine A** (the static skill-coverage gate, `crm/tests/skill_coverage.py`) **stands** and is complemented here by a new static lint. ADR 0015's **Machine B** (absolute pass-rate, no A/B control, ~12–15 trial-plan tasks, both targets unioned, periodic CI-scheduled) and ADR 0016's persist-then-analyze efficacy review are **replaced** by the paired-condition, demand-sourced, on-demand design below. The single load-bearing reversal: **paired with/without-skill conditions are now canonical, not an opt-in counterfactual** — attribution ("did the skill help?") is a headline goal of this effort, so it is paid for by default.

## Context

Decided across the wayfinder map [#874](https://github.com/Gharib89/crm/issues/874) (grilling sessions, 2026-07-17), which set out to design — as a spec + ADR, not to build — a behavioral evaluation system for the shipped `crm` skill (`crm/skills/`) able to answer four questions:

1. **Skill lift** vs a no-skill baseline — does the skill actually help an agent?
2. **Regression** when a PR touches the skill — did an edit make it worse?
3. **Cross-model / cross-agent** performance — how does lift vary by model and harness?
4. **Static best-practices conformance** — does the skill stay well-formed?

ADR 0015 proposed answering these with an absolute pass-rate behavioral eval and deliberately dropped the A/B control arm to halve runs; ADR 0016 then revived that control arm as an opt-in and added a persist-then-analyze efficacy review. The map revisited the whole design from the SkillsBench methodology outward (research tickets [#875](https://github.com/Gharib89/crm/issues/875)/[#876](https://github.com/Gharib89/crm/issues/876)/[#877](https://github.com/Gharib89/crm/issues/877)) and reached a materially different, fuller architecture: attribution is the point, so paired conditions are canonical; the corpus is sourced from real public demand, not the trial plan or the skill's own docs; runs are discretionary, not CI-scheduled. This ADR records the resulting decisions; the implementation-ready detail lives in the [skill-eval system spec (#888)](https://github.com/Gharib89/crm/issues/888).

## Decision

Two independent machines, split on the deterministic/behavioral line (the split ADR 0015 got right, with a redefined Machine B).

### Machine A — static conformance (deterministic, per-PR CI)

Two offline pytest gates, no agent runs, both blocking every PR:

- **Skill-coverage gate** (retained from ADR 0015, unchanged): `crm/tests/skill_coverage.py` — CLI reconciliation via the `walk_commands()` catalogue (dead references + top-level-group completeness with a `WAIVED` list).
- **Skill lint** (new, [#883](https://github.com/Gharib89/crm/issues/883)): four deterministic, hard-fail rules over the shipped skill text/structure only — (1) **self-containment** (no repo-path refs — `docs/**`, `CONTEXT.md`, links escaping the skill dir), (2) **internal link integrity** (every `reference/*.md` reachable from the router, every relative link resolves, no orphans), (3) **thinness budgets** (`SKILL.md` ≤ 300 lines, each `reference/*.md` ≤ 250 lines — line counts, no tokenizer), (4) **frontmatter contract** (valid YAML; `name` correct; `description` present, within cap). New module pair `crm/tests/skill_lint.py` + `test_skill_lint_gate.py`, importing `skill_files()` from `skill_coverage.py` so file discovery stays single-source; `WAIVED`-style escape hatch. Fuzzy rules (description *quality*, no-restated-flags) are **excluded** — they can't be statically distinguished from legitimate examples, and stay where judgment lives (the `writing-great-skills` review at edit time; the advisory L2 judge in eval runs).

### Machine B — behavioral eval (paired, live, on-demand, never CI)

- **Methodology canon** (adapt SkillsBench; build our own harness — [#878](https://github.com/Gharib89/crm/issues/878)): (1) **paired conditions** — every task runs with-skill and no-skill against identical prompt + org state; lift = the delta; (2) **deterministic programmatic verifiers** — no LLM judge as the primary grader; (3) **binary pass per trial** — report pass-rate delta and Hake normalized gain `g = (pass_skill − pass_bare) / (1 − pass_bare)`, reported as **N/A and excluded from any mean when `pass_bare == 1`** (no headroom → gain undefined); (4) **invocation measured separately** from success. BenchFlow/Docker are rejected: a live org is shared mutable state outside any container, our live-e2e infra already solves creds/fixtures/teardown, and `bench`'s trial scheduler collides on one shared org.
- **Corpus** ([#879](https://github.com/Gharib89/crm/issues/879), validated by pilot harvest [#885](https://github.com/Gharib89/crm/issues/885)): ~30 tasks sourced from **real public demand** (Dynamics community forums, Stack Overflow, Reddit, this repo's issues + `DISCOVERED_BUGS.md`; firsthand as a traceable secondary), **never the skill's own docs**. Each task double-tagged — **module** (a `reference/*.md` file or `uncovered`) × **kind** (`do` = org-mutating, graded on org state; `feasibility` = graded against an evidence-backed answer key). Three tiers (T1 single-command, T2 workflow, T3 trap), weighted T2/T3. Demand-weighted slot allocation; calibration filter drops non-discriminating tasks (baseline 3/3 → smoke sentinel; with-skill 0/3 → triage).
- **Grading, two layers with a hard line** ([#879](https://github.com/Gharib89/crm/issues/879)): **L1 deterministic binary** is the *sole* input to pass rate, normalized gain, and regression verdicts — org-state reads for `do`, field-by-field answer-key match for `feasibility`. **L2 LLM judge** is advisory only, blind to condition, model/rubric pinned — never gates, never enters lift stats.
- **Target** ([#880](https://github.com/Gharib89/crm/issues/880)): **live org, one per run** (cloud **or** on-prem, default `agent-cloud`), reusing the e2e profile/host-guard/fixture patterns. Mocked/recorded is ruled out (an agent picks its own path; cassettes break; verifiers need real state). Containment = fixture-seeded `EVAL-<runid>-…` records + post-run marker sweep on the opted-in test org (a backstop, not a wall — accepted risk, same stance as the e2e suite). **The org is reset between the two legs of a pair** — a full fixture reseed (or snapshot/restore) before the second leg, because marker sweep only removes tagged records and the first leg may make unmarked mutations that would otherwise skew the comparison; both legs must start from identical state (the attribution keystone). Per-target score series are never merged.
- **Harness** ([#881](https://github.com/Gharib89/crm/issues/881)): headless **`claude -p` subprocess** (not the SDK — the eval is fire-one-prompt → verify-org-state; a subprocess gives per-trial env/cwd/`CLAUDE_CONFIG_DIR` isolation, no new dependency, and extends to `codex exec`). Paired conditions share an **identical hermetic env** (temp `CLAUDE_CONFIG_DIR`, temp cwd, identical flags); the treatment differs by **exactly one act** — a real `crm skill install` into the temp config dir. `crm` is the **built wheel** in a per-session venv (never an editable/repo install), with a fixture-seeded `CRM_HOME` profile. Model is a per-run parameter (resolved id in metadata, per-model series never merged). A thin **runner contract** `(workspace, config dir, prompt, model, skill on/off) → (artifacts, cost, transcript, invocation-signal-or-null)` with Claude Code as the sole v1 implementation; Codex is specified-not-built (injection + invocation-tracking are non-portable → nullable). Guardrails: `--allowedTools Bash,Read,Grep,Glob,Skill`, **web off both sides** — and because denying the `WebSearch`/`WebFetch` *tools* does not stop `curl`/Python HTTP from the allowed `Bash`, the runner **blocks outbound network at the sandbox level** — **Claude Code's built-in Bash sandbox** (bubblewrap + socat on Linux/WSL2, no root), which confines each Bash command to the org host via `network.allowedDomains` while the main `claude` process keeps normal network, with `failIfUnavailable` making the run **fail closed** (abort, never silently run unsandboxed) — applied identically on both legs, so hermeticity is real rather than tool-deep; `--max-turns 50` + 10 min/trial wall-clock (a cap-hit is a distinct outcome counting as fail). Trials serialize against the one live org.
- **Cadence** ([#882](https://github.com/Gharib89/crm/issues/882)): **discretionary, no gates anywhere** — no CI trigger, no merge gate, no schedule; runs when the maintainer has subscription headroom. Presets: **full** (whole corpus, paired, k≥3 — the only *reportable* kind), **smoke** (~8 tasks, with-skill only, k=1), **regression-check** (with-skill only, baseline leg skipped). `k` defaults to 1; any quoted lift must come from a k≥3 full run; runs of different k are never merged.
- **Regression semantics** ([#882](https://github.com/Gharib89/crm/issues/882)): advisory, never blocking. Baseline = newest *reportable* run of the same series (model × target × k). Metric = **with-skill pass rate** (not lift). Flags: macro pass rate drops **>5 pp**, or any task flips **all-pass → all-fail** (`k/k → 0/k` at the run's configured `k`, not a fixed 3). Human judges.
- **Storage & reporting** ([#886](https://github.com/Gharib89/crm/issues/886)): in-repo `evals/results/<run-id>/` — `run.json` (metadata + aggregates + a computed `reportable` stamp) and `trials.jsonl`. Reportable full runs are committed by **force-adding the explicit artifact paths** (`git add -f evals/results/<run-id>/{run.json,trials.jsonl,report.md}`), never the whole run dir — `git add -f` overrides `.gitignore`, so the transcripts/`run.log` stay untracked only because they are never named, not because an ignore rule can survive `-f`. Smoke/exploratory runs and transcripts are never committed. Baseline lookup = scan `run.json`s, filter same series + reportable, take newest. Surfaces: a CLI summary on stdout **every** run; a committed `report.md` per reportable run; a derived `matrix.md` (cross-model/agent view, lift-vs-own-baseline across harnesses). `.gitignore` ignores `evals/results/*` except `matrix.md` (a convenience so exploratory runs don't clutter `git status`; the guarantee that transcripts/logs stay out is the explicit-path commit rule, not the ignore file).

## Considered options

- **Adopt SkillsBench / BenchFlow as the runtime** (even against cloud, which removes the reachability objection) — rejected. Statefulness (a live org is shared mutable state outside the container), duplication of already-solved live-e2e infra, `bench`'s colliding trial scheduler, and a young py≥3.12/Docker dependency for a never-upstreamed private eval. Its *methodology* (paired conditions, deterministic verifiers) is adopted as canon.
- **Absolute pass-rate, no A/B control arm** (ADR 0015's core choice) — **reversed.** Attribution is a headline goal (#1 skill lift); measuring it is the reason the eval exists, so the 2× live cost of the paired run is paid by default on full runs. Cost is instead controlled by the smoke/regression presets (which skip the bare leg), not by dropping attribution.
- **Both targets unioned into one coverage number** (ADR 0015) — replaced by **one target per run** with per-target series never merged: cheaper per run, and cross-target pass rates aren't comparable anyway.
- **Periodic CI-scheduled runs writing `baseline.md`** (ADR 0015) — replaced by **discretionary, on-demand** runs. Live orgs + VPN + agent latency make a schedule brittle for one maintainer; regression is advisory, so a gate buys nothing.
- **claude-agent-sdk driver** — rejected for the `claude -p` subprocess: no multi-turn steering is needed, the subprocess isolates paired conditions exactly, and it adds no dependency to a pyright-strict repo while extending to other agent CLIs.
- **Mocked / recorded D365 target** — rejected: an agent-under-eval chooses its own command path, so cassettes break on divergence, and the org-state verifiers need real state.
- **`evals/skill/runs/` layout with a human-gated `efficacy.md`** (ADR 0016) — replaced by `evals/results/<run-id>/` with `run.json`/`trials.jsonl` and a computed `reportable` stamp; the derived `matrix.md` replaces the hand-promoted trend file.
- **Leaf-/flag-level static coverage, or a description-quality lint** — rejected: they fight the router design (ADR 0009) or are irreducibly fuzzy; the four deterministic lint rules plus the retained coverage gate are the static surface.

## Consequences

- **The ADR record is reconciled**: ADR 0015 is marked *partially superseded* (Machine A stands, Machine B replaced) and ADR 0016 *superseded*; an implementer reads one coherent design, not three conflicting ones.
- **Full runs cost 2× the live-org work** of a single-condition run (both legs of every pair). Bounded by discretionary cadence and by the smoke/regression presets that skip the bare leg.
- **Validity rests on three legs**: hermetic isolation (the treatment must differ from control by exactly the skill install), verifier quality (a wrong `feasibility` answer key or a loose `do` verifier silently corrupts the number), and demand-sourced corpus discipline (sampling the skill's own docs would teach to the test and inflate lift).
- **Nothing is built by this ADR.** Implementation is a separate effort; the [spec (#888)](https://github.com/Gharib89/crm/issues/888) is the build-ready detail and the map [#874](https://github.com/Gharib89/crm/issues/874) is the decision trail.
- The eval lives at `evals/` at the repo root, **not shipped in the wheel** — same stance as ADR 0015's Machine B.

## Amendments

- **2026-07-20 — sandbox mechanism ([#906](https://github.com/Gharib89/crm/issues/906)).** The Harness clause left the outbound-web block's *mechanism* open ("network namespace / firewall / no-network sandbox"). The first implementation ([#890](https://github.com/Gharib89/crm/issues/890)/[#905](https://github.com/Gharib89/crm/issues/905)) chose a **root network namespace** that caged the *whole* `claude` process — which also blocked the model driver's own `api.anthropic.com` egress, so every turn died at `ENOTIMP` and both legs produced a false `0% vs 0%` null. Resolved by taking the "no-network sandbox" option the clause already permitted: **Claude Code's built-in Bash sandbox** (bubblewrap + socat), which confines only the agent's Bash subprocesses to the org host (`network.allowedDomains`) while the main process keeps normal network. It needs **no root**, catches every Bash child process, and cannot be self-bypassed (`allowUnsandboxedCommands: false`); `failIfUnavailable: true` is the fail-closed gate. The netns/nftables/veth machinery and #905's root-launch scaffolding (`setpriv` de-privileging, bin resolution, creds/`HOME` chown) are removed. Status stays **accepted** — only the mechanism changed, not the design.
- **2026-07-20 — fail-closed is a runtime probe, not just `failIfUnavailable` ([#906](https://github.com/Gharib89/crm/issues/906)).** Validating the built-in sandbox surfaced two gaps the mechanism-swap bullet glossed. (1) **Workspace trust** — Claude Code will not fully initialize the sandbox for an *untrusted* workspace; the eval's fresh `HOME` has never been through the trust dialog, so it ran degraded (proxy env injected, proxy never started → every request, org included, died at the dead proxy). The harness now writes a trust record (`$HOME/.claude.json`) for the agent's cwd (trust-only, no repo/memory, so isolation holds). (2) **`failIfUnavailable` is binaries-only** — it proves bubblewrap/socat exist, *not* that the proxy started and enforces, so a host where the proxy is dead (false `0% vs 0%` null) or up-but-leaky (a denied host still egresses → inflated lift) passes it yet silently breaks isolation. The real fail-closed gate is therefore a **runtime preflight probe**: one sandboxed `claude -p` must show the org reachable **and** a non-org host blocked, else the paired front door aborts. **Known limitation:** on **WSL2** the sandbox proxy startup is unreliable (races between dead / up-but-leaky), so the paired eval's live run must target a host where the built-in network sandbox is reliable (native Linux); the preflight makes an unreliable host fail loudly rather than measure garbage. Status stays **accepted**.
- **2026-07-24 — self-seeding is the corpus canon; the `fixture:` field is deferred ([#925](https://github.com/Gharib89/crm/issues/925)).** The Target clause specced containment as *"fixture-seeded `EVAL-<runid>-…` records"* with *"a full fixture reseed (or snapshot/restore) before the second leg."* The walking skeleton ([#890](https://github.com/Gharib89/crm/issues/890)) never built a `fixture:` field — `taskspec.py` parses none — and the established, deliberately-minimal pattern is **self-seeding**: the `do`-task agent creates its own population as step 1, the `end_state` predicate grades the final org state, and `cleanup_org` runs **unconditionally before each leg** (`evals/skill/runner.py`). This preserves the **attribution keystone intact** — both paired legs still start from identical (empty) state, so lift is uncontaminated — which is the sole guarantee the fixture-reseed clause existed to provide. `fixture:` is therefore **not built by design, not by omission**: it would add a seed/snapshot subsystem justified only by the one case self-seeding can't reach — a task needing a non-trivial *pre-existing* population the agent must **not** create itself — and no corpus task needs that yet (the bulk cluster [#895](https://github.com/Gharib89/crm/issues/895)/PR #924 confirmed all three `do`-tasks self-seed cleanly). It does **not** buy back the state-vs-path limit (an org-state predicate can't distinguish e.g. bulk-update from create-with-the-target-value; that stays with the advisory L2 judge + the baseline-3/3 calibration filter — neither of which `fixture:` would change). **Reopen when a concrete task requires a pre-existing population**; the schema addition (seed-prefixed records vs snapshot/restore vs a declarative `fixture:` block, and its interaction with the marker sweep) is deferred to that trigger. Status stays **accepted** — the design's keystone is unchanged; only the unbuilt containment mechanism is reconciled to the built reality.
