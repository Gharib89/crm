# Keeping the agent skill in sync with the CLI

## Source of truth

Two agent skills ship, each a thin `SKILL.md` router plus `reference/*.md`
files loaded on demand: `crm/skills/` (the `crm` skill) and
`crm/migration-skill/` (the `crm-migration` skill, ADR 0033). The package ships
both trees (`package_data` in `setup.py`; bundled in `crm.spec`) and
`crm skill install --skill <name>` (default `crm`) copies one into an agent's
skill directory, at `<name>` under the target's root:

| Target | Destination |
| --- | --- |
| `claude` | `~/.claude/skills/<name>/` |
| `copilot` | `~/.copilot/skills/<name>/` |
| `cursor` | `~/.cursor/rules/<name>/` |

```bash
crm skill install --target claude --force
```

## Two rules that keep the skill healthy

1. **Self-contained.** The skill ships to users who have only the skill, not this
   repo. No shipped skill file may link to a repo-only path (`docs/**`,
   `GLOSSARY.md`, `../`) or assume any repo file is present. Inline what the agent
   needs (labels, templates, tables). The only assumed externals are the installed
   `crm` binary and, for the feedback flow, the `gh` CLI.
2. **Never restate flags.** `crm describe [group]` and `crm <group> --help` emit
   every command, option, choice, default, and envvar straight from the live Click
   tree — they cannot drift. The skill states only what they cannot: workflows,
   gotchas, and the JSON contract. Maintenance test: **if a line could be
   regenerated by `crm describe`, delete it.**

Nothing enforces "never restate flags": it is a review rule. `crm/tests/test_skill_lint_gate.py` (via `crm/tests/skill_lint.py`) enforces self-containment, a router line cap, per-reference line and byte caps, and that the status words the migration skill quotes match the code's enums.

## When the CLI changes

Use the **`writing-for-agents`** skill (`.claude/skills/writing-for-agents/`) as
the authority for skill structure, progressive disclosure, and description-writing
whenever you edit the skill — the two crm-specific rules above override it on conflict.

After adding or changing a command, update the relevant `crm/skills/reference/*.md`
(workflows and gotchas — not flag *definitions* already in `--help`; flags appear in examples) and the SKILL.md map if a new group appeared,
then reinstall with `--force`. To detect drift against an install:

```bash
diff -r crm/skills ~/.claude/skills/crm
```

## Four checks before the PR opens

The four classes of miss below recurred across merged PRs (retro #1240). This
section is their single home; the ship profile (`docs/agents/ship.md`, `## Docs
sync`) points here instead of restating them. Run each
before `/ship` opens the PR, and name the pass in the PR body.

1. **Probe every doc claim.** Each field, key, flag, default or behavior that a
   new or edited doc, skill or help sentence names is checked against the code or
   `crm <group> <verb> --help` before the commit (#1086, #1111, #1121, #1162,
   #1187, #1230, #1234). Open the symbol or run the help; a sentence copied from
   the issue or from memory is a claim, not a fact.
2. **Map each acceptance criterion to a named assertion.** Before the PR opens,
   list every criterion beside the test node (or the doc check) that proves it,
   and add the missing one; an unmapped criterion is untested (#1087, #1132,
   #1216, #1225, #1236). Record each pairing as a
   `Criterion <n>:` line in the ship Run file, which the merge summary reads;
   outside ship, list it under the PR body's `## Change outline`.
3. **Give each new capability its README row and help text.** Every new flag or
   output field gets its `README.md` row (where the capability is user-facing)
   and its Click group or option help text, in the docs-sync step (#1089, #1113,
   #1118, #1217).
4. **Check the diff against the issue's scope.** Read the issue's `Out of scope`
   and `Decision` lines against `git diff --stat` before review; a changed path
   no criterion or logged deviation explains comes out (#1111, #1185).

Ship's phases are fixed and its profile carries facts, not new checks, so these
live as repo rules. A profile field for criterion mapping or a scope check would
be an upstream change to `Gharib89/skills`.

## The bug loop used to build CRMWorx

While building the walkthrough, defects were handled with a hybrid policy:

- **Trivial / single-function:** write a failing test in `crm/tests/`, fix in `crm/`,
  re-run, continue — the fix lands in the same session.
- **Larger:** file a triaged GitHub issue with a minimal repro, work around, continue.

Issues filed during the run are tracked in
[GitHub Issues](https://github.com/Gharib89/crm/issues).
