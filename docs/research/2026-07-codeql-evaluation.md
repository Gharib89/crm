# CodeQL evaluation for Gharib89/crm

**Date:** 2026-07-11
**Feeds:** wayfinder ticket #822 on map #819 (code-review stack)

**Question:** Should the public repo Gharib89/crm (Python 3.9+ CLI for Dynamics 365, ~46k product LOC / ~129k total Python incl. tests) enable GitHub code scanning with CodeQL, given the existing gates (pyright strict on `crm/core/*` + `crm/utils/d365_backend.py`, offline pytest in CI, CodeRabbit OSS being adopted, Copilot code review active)? What would CodeQL catch that these don't?

## TL;DR

**Go — enable CodeQL default setup with the `security-extended` suite.** It is free for this public repo, needs no build or maintenance, and is the only exhaustive dataflow/taint analysis in the stack. Expected alert volume is **very low (likely 0–3 alerts total)** — precisely because this is a CLI, not a web service: CodeQL's Python taint queries fire on *remote* (web-framework) sources by default, and this repo has none. The realistic catches are the non-taint heuristic queries: `py/clear-text-storage-sensitive-data` on the deliberate plaintext `_secret` fallback (one-time "won't fix" dismissal), and `py/tarslip`-family checks guarding the self-update extractor (`crm/core/update.py` already hand-guards this — CodeQL documents recognizing exactly those guards). The real value is a permanent, exhaustive regression tripwire on the security-sensitive surfaces (credential storage, archive extraction, subprocess to `pac`, XML parsing) at zero marginal cost — cheap insurance, not a noise source.

### Which CodeQL Python queries map onto this — fire vs. irrelevant

Query metadata below is from the per-query help pages under [codeql.github.com/codeql-query-help/python/](https://codeql.github.com/codeql-query-help/python/); each page lists the suites that include the query.

**Plausible alerts (small, finite set):**

- **[`py/clear-text-storage-sensitive-data`](https://codeql.github.com/codeql-query-help/python/py-clear-text-storage-sensitive-data/)** — precision *high*, severity error (7.5), **in the default `python-code-scanning.qls` suite**. Sources are name-heuristic "sensitive data" (passwords/secrets), not remote taint — so it *can* fire on a CLI. `save_profile_secret_plaintext` (`crm/core/session.py:119`) writes a value flowing from password prompts/flags into a JSON file in clear text. This is the single most likely genuine alert. It's *by design* (documented keyring→0600-plaintext fallback), so the outcome is a one-time dismissal ("won't fix") — but it's also exactly the code you want a permanent tripwire on (e.g. a future regression dropping the `0o600` or widening what lands in the file). Sibling **[`py/clear-text-logging-sensitive-data`](https://codeql.github.com/codeql-query-help/python/py-clear-text-logging-sensitive-data/)** watches the logging side; currently clean (grep found no secret-into-logger flow), and keeping it clean is the point.
- **[`py/tarslip`](https://codeql.github.com/codeql-query-help/python/py-tarslip/)** — precision *medium*, severity error (7.5), **security-extended only** (not in the default suite). Fires on `tarfile.extract/extractall` with unvalidated member paths **regardless of where the archive came from** (no remote source needed). `update.py:417` is the one `tarfile.extractall` in the repo. The query help explicitly documents recognizing the guards this code uses — checking entry paths for `..` elements, `os.path.isabs`, raising on unsafe paths — so the existing `_is_safe_member` loop should suppress it; if the guard recognition doesn't connect (medium precision), it's one triageable near-FP on code that is already correct. Note there is **no zip-slip twin for `zipfile.extractall`** in the Python pack (tarslip covers `tarfile` only), so the zip branch of `_extract` is guarded by code review, not CodeQL.
- **[`py/overly-permissive-file`](https://codeql.github.com/codeql-query-help/python/py-overly-permissive-file/)** / **[`py/insecure-temporary-file`](https://codeql.github.com/codeql-query-help/python/py-insecure-temporary-file/)** — the repo's file-permission and tempfile hygiene is currently exemplary (`0o600` via `os.open` O_EXCL, `tempfile.mkstemp` + `os.replace` everywhere; no `mktemp`). Zero expected alerts; value is regression coverage on `session.py` / `metadata_cache.py` / the atomic-write helpers.

**Likely silent despite matching surface — because the taint source model doesn't reach a CLI:**

- **[`py/command-line-injection`](https://codeql.github.com/codeql-query-help/python/py-command-line-injection/)** (precision high, 9.8, default suite) and **[`py/path-injection`](https://codeql.github.com/codeql-query-help/python/py-path-injection/)** (precision high, 7.5, default suite) — sinks match (`subprocess.run` in `solutionpackager.py`; ubiquitous `open()`/`Path` ops on `--folder`/`--zipfile` flags), but the sources are **remote user input** (web-framework request objects). CodeQL's Python `RemoteFlowSource` catalog is web-framework-centric ([RemoteFlowSources.qll](https://github.com/github/codeql/blob/main/python/ql/lib/semmle/python/dataflow/new/RemoteFlowSources.qll)); Click/argv are not sources by default. So these will not fire on flag-derived flows. That is *correct* for a CLI's attacker model (the local user already has shell), not a coverage gap.
- **[`py/xxe`](https://codeql.github.com/codeql-query-help/python/py-xxe/)** (precision high, 9.1, default suite) and **[`py/xml-bomb`](https://codeql.github.com/codeql-query-help/python/py-xml-bomb/)** (precision high, 7.5, default suite) — `py/xml-bomb` explicitly names `xml.etree.ElementTree` as an entity-expanding parser (recommendation: `defusedxml`), and this repo parses org-supplied XML with ElementTree throughout. **But** both queries require an *untrusted (remote) source* flowing into the parse. Two things keep them silent here: (a) local files (customizations XML) are under the disabled-by-default `file` threat model; (b) I verified in the CodeQL Python library that `requests` responses are modeled as HTTP-client taint steps but **not** as `RemoteFlowSource` ([Requests.qll](https://github.com/github/codeql/blob/main/python/ql/lib/semmle/python/frameworks/Requests.qll) — no `RemoteFlowSource` subclass), so Web-API-response XML (formxml etc.) isn't a source either. Substantively: a hostile *solution zip* or customizations file crossing the org boundary could still carry an entity-expansion bomb into `ET.fromstring` — a real (low-severity, DoS-only) consideration that CodeQL will *not* surface under the default threat model. The size cap in `solution_transfer.py` (`_MAX_SOLUTION_XML_BYTES`, 64 MiB pre-decompression check) mitigates the zip-side blowup but not entity expansion itself.
- **[`py/full-ssrf`](https://codeql.github.com/codeql-query-help/python/py-full-ssrf/)** / `py/partial-ssrf` — `requests.get(f"{base_url}/...")` in `update.py:65,349,361` is the right sink shape, but `base_url` comes from config/constants, and again no remote source exists. Silent.

**Irrelevant by construction (grep-verified):** SQL injection, all web-framework queries (reflected XSS, CSRF, open redirect, cookie flags), template injection, deserialization (`py/unsafe-deserialization` — no pickle/yaml), `py/use-of-weak-crypto` (only SHA-256), `py/insecure-randomness` (jitter only), `py/request-without-cert-validation` (no `verify=False`).

**Threat-model extension (the lever if more is wanted later):** the CodeQL library ships a threat-model taxonomy (`remote` default; `local` = command-line args, environment, file reads, databases — [workflow configuration options](https://docs.github.com/en/code-security/reference/code-scanning/workflow-configuration-options)). The Python QL library has the `ThreatModelSource` machinery (e.g. `open()` reads tagged kind `"file"` in [Stdlib.qll](https://github.com/github/codeql/blob/main/python/ql/lib/semmle/python/frameworks/Stdlib.qll); [Concepts.qll](https://github.com/github/codeql/blob/main/python/ql/lib/semmle/python/Concepts.qll) defines `ActiveThreatModelSource`), **but** the GitHub docs state threat-model *settings* are "supported only by analysis for Java/Kotlin and C#" during preview — so for Python this is advanced-setup/CLI territory (`--threat-model local`) and of marginal value for a CLI anyway (would mostly manufacture alerts about the local user attacking themselves). Not recommended initially.

## 2. Overlap with the existing gates

| Gate | What it covers | What it misses that CodeQL adds |
|---|---|---|
| **pyright strict** (`crm/core/*`, `d365_backend.py`) | Types, None-safety, unreachable code, signature misuse — per-expression, exhaustive within its scope | Zero *semantic dataflow*: pyright cannot say "this value that came from a password prompt reaches a plaintext file write" or "this archive member name reaches `extractall` unvalidated". Also 250 of 370 py files are only basic-mode. |
| **pytest (offline, CI)** | Behavior the tests encode — including some security behaviors (the extractor guards, 0600 modes have tests) | Only tested paths; a new unguarded `extractall` or a secret routed to a log line ships silently unless someone writes the test. |
| **Copilot code review** (auto round 1) + **CodeRabbit OSS** (per-PR, being adopted) | LLM review of the PR diff: style, logic, some security pattern-matching | **Non-exhaustive and diff-scoped by construction.** No whole-program dataflow; can't trace a source in file A to a sink in file B introduced two PRs apart; stochastic (same diff can get different findings). CodeRabbit runs CodeQL-*adjacent* linters but not CodeQL-class interprocedural taint analysis. |
| **CodeQL** | Exhaustive, deterministic, whole-repo dataflow/taint analysis on every PR + weekly schedule; alerts persist as a tracked backlog with status | The only one of the four that is exhaustive over the whole codebase per scan, and the only one doing interprocedural taint tracking at all. |

Honest scope note: CodeQL's exhaustiveness is *within its query set and source model* — as §1 shows, the default remote-source model means most taint queries idle on a CLI. The unique value here concentrates in the heuristic-source queries (cleartext storage/logging), archive/file-permission checks, and future-proofing (any web/service surface, a new `shell=True`, a new extractall would light up immediately and deterministically).

## 3. Setup cost

- **Default setup** ([configuring default setup](https://docs.github.com/en/code-security/code-scanning/enabling-code-scanning/configuring-default-setup-for-code-scanning)): a few clicks in *Settings → Code security*; Python is in the no-special-configuration list ("Analysis of JavaScript/TypeScript, Go, Ruby, Python, and Kotlin code does not currently require special configuration" — no build needed). It auto-creates the workflow, scans on **pushes, pull requests, and a weekly schedule**, and lets you pick the query suite in the UI. No YAML to maintain; GitHub updates the CodeQL engine/packs for you. Advanced setup (committed `codeql.yml` workflow) is only needed for custom queries/threat models/path filters — not warranted here.
- **Suite choice** ([built-in query suites](https://docs.github.com/en/code-security/code-scanning/managing-your-code-scanning-configuration/built-in-codeql-query-suites)): `default` = high-precision, few FPs; `security-extended` = default plus "additional queries with slightly lower precision and severity". **Pick `security-extended`**: it's what pulls in `py/tarslip` (medium precision — see §1), and on a repo where the default suite will produce ~0–2 alerts, the extended suite's extra noise budget is trivially affordable.
- **Cost: $0.** Prerequisite for default setup is that the repo is "publicly visible, or GitHub Code Security is enabled" — i.e. public repos need no Advanced Security/Code Security license ([same page](https://docs.github.com/en/code-security/code-scanning/enabling-code-scanning/configuring-default-setup-for-code-scanning)). The scans run on Actions, and "GitHub Actions usage is free … for public repositories that use standard GitHub-hosted runners" ([Actions billing](https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions)).
- **Scan duration** (estimate, not a doc citation): pure-Python extraction with no build on a ~130k-LOC repo typically lands in the low single-digit minutes per run on a hosted runner — comparable to the existing pytest CI job, and it runs as a parallel check, not a serial gate on anything else.

## 4. Noise level

- **Precision tiers:** the default suite is deliberately curated for "highly precise" queries that "return few false positive code scanning results"; security-extended knowingly admits "slightly lower precision" ([built-in suites](https://docs.github.com/en/code-security/code-scanning/managing-your-code-scanning-configuration/built-in-codeql-query-suites)). Per-query precision is published on each query-help page (§1: everything likely to fire here is *high* except tarslip's *medium*).
- **PR check behavior:** annotations only appear for alerts whose lines are in the PR diff, and by default the check **fails only on new alerts of severity `error`, or security severity `critical`/`high`** — lower severities surface as warnings without blocking ([triaging alerts in PRs](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/triaging-code-scanning-alerts-in-pull-requests)). Threshold is adjustable in repo settings. Pre-existing alerts never fail a PR.
- **Triage:** persistent alert list with dismissal reasons *false positive / won't fix / used in tests* + optional comment; dismissal sticks across scans ([same page](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/triaging-code-scanning-alerts-in-pull-requests)). So the expected `_secret`-plaintext alert is a one-time 30-second dismissal, not a recurring nag.
- **Python FP track record (primary sources):** the CodeQL changelog shows the exact queries relevant here have had FP classes acknowledged and fixed — usernames/account info dropped from the sensitive-data model "since this led to many false positives" ([CodeQL 2.8.0](https://codeql.github.com/docs/codeql-overview/codeql-changelog/codeql-cli-2.8.0/)), and the `certificate` classification excluded from both cleartext queries ([CodeQL 2.19.0](https://codeql.github.com/docs/codeql-overview/codeql-changelog/codeql-cli-2.19.0/)). Reading: the Python cleartext/path-injection families do generate FP reports in `github/codeql` issues, and the team actively prunes them. On *this* repo the exposure is bounded by §1's analysis: almost no taint sources exist, so the structural FP risk of taint queries is mostly moot.

## 5. Recommendation

**Go. Enable default setup with `security-extended`, today, in about five minutes.**

Rationale, sized to this repo:

1. **Cost ≈ 0:** free (public repo, free Actions minutes), no build config for Python, no workflow file to own, engine/pack updates are GitHub's problem.
2. **Expected noise ≈ 0:** realistic initial yield is one deliberate-design alert (`py/clear-text-storage-sensitive-data` on the plaintext `_secret` fallback → dismiss "won't fix") and possibly one medium-precision tarslip near-FP on already-guarded code. The PR check only fails on *new* error/critical/high alerts, so the existing 3-round Copilot/CodeRabbit review budget is untouched.
3. **It fills the one genuine hole in the stack:** nothing else does exhaustive, deterministic, whole-repo dataflow. Its day-1 findings will be minimal precisely because the attacker model is thin (trusted local user; the code already guards the boundary-crossing surfaces well) — the payoff is the *tripwire*: any future unguarded `extractall`, `shell=True`, secret-to-log flow, or dropped `0o600` becomes a blocking, line-annotated PR check instead of a hope that an LLM reviewer notices.
4. **Set expectations accordingly:** this is insurance, not a findings engine. Do not budget triage time beyond the initial pass; do not bother with threat-model extensions (`local` sources) — Python threat-model settings aren't supported in default setup anyway, and taint-from-argv is the wrong model for a CLI.
5. **One follow-up worth a separate look** (out of CodeQL's reach under the default model, flagged not fixed — repo is read-only for this research): org-supplied XML (solution zips, customizations) is parsed with stdlib `ElementTree`, which `py/xml-bomb`'s own help calls out for internal entity expansion; `defusedxml.ElementTree` is the documented drop-in. Low severity (DoS-only, ElementTree refuses *external* entities), but it's the one boundary-crossing input CodeQL will stay silent about.
